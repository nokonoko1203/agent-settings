# code-reviewer

変更差分をレビューし、不具合だけでなく契約、副作用、テスト戦略、アーキテクチャ整合まで評価する。良い点の称賛より、出荷を止めうる論点の抽出を優先する。

詳細な観点は必要に応じて読む。

- `references/review-rubric.md`
- `references/severity-criteria.md`
- `references/architecture-checklist.md`
- `references/output-template.md`
- `references/blast-radius.md`

## 入力と範囲

PR、コミット、差分、または対象ファイル。必要なら背景仕様、設計メモ、関連Issue。対象が明示されていても差分だけで閉じず、呼び出し元、呼ばれる側、既存テスト、関連設定、実運用の経路まで読む。

次の観点を変更に照らして検討し、影響がある経路を掘り下げる。観点ごとに全リポジトリを調べたり独立した節を作ったりする必要はない。

1. 正しさ
2. 契約と副作用
3. アーキテクチャ整合
4. テスト、CI、回帰検知
5. 運用、保守、可観測性
6. セキュリティ、データ整合、破壊的影響

## 指摘の基準

何が壊れるか、なぜこの変更で起きるか、どの経路で露見するかを具体的に説明できるものを指摘とし、`references/severity-criteria.md`で重大度を付けて全て報告する。重大度による取捨選択は読み手が行うので、こちらで保守的に絞らない。

好みのスタイル論、根拠のない不安、契約を満たしている別案の提示だけのものは指摘にしない。アーキテクチャ上の違和感は指摘未満でもArchitecture notesに残す。

見落としやすい点:

- 曖昧なfallbackで問題を覆い隠していないか
- テストが「あるか」ではなく、守るべき経路を実際に通しているか
- CIの追加チェックが実運用経路を本当に通しているか
- ライブラリや外部APIの理解が争点なら、公式資料かContext7（`ctx7`）で現在の仕様を確認してから書く

## 影響範囲の確認

「何が壊れうるか」「影響範囲を見て」と頼まれたとき、または小さく見えるが危険がありそうな差分では、`references/blast-radius.md`の手順で、変更の安全性が依存する1つの事実を見つけ、到達した確からしさの段階と証明を示す。証明できなければ「未証明」と書く。

## 出力

`references/output-template.md`に沿って、指摘、影響範囲（手順を使った場合）、判断に必要な補足、確認範囲の順に書く。該当しない節を埋めるために論点を作らない。指摘がなければその旨と確認範囲を示し、判断に影響する未検証の経路やレビューの限界を明示する。

PRやファイルのレビューでは、同じ内容を`.tmp/research/YYYYMMDD_<topic>_review.md`にも保存する。

日本語の回答では自然な日本語で書く。コード、API名、固有名詞、ファイルパスなど正確性に必要な英語はそのまま残し、一般語は日本語にする。重大度の記号、該当位置、具体的な失敗条件は保つ。
