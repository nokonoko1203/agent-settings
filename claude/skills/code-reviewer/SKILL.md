# code-reviewer

変更差分をレビューし、不具合だけでなく契約、副作用、テスト戦略、アーキテクチャ整合まで評価する。良い点の称賛より、出荷を止めうる論点の抽出を優先する。

詳細な観点は必要に応じて読む。

- `references/review-rubric.md`
- `references/severity-criteria.md`
- `references/architecture-checklist.md`
- `references/output-template.md`
- `references/blast-radius.md`

## Codexとの相互レビュー

Claude Codeで動いているときは、Codex（sol）にも同じ対象を別にレビューさせ、自分のレビューと統合して判断する。Codexの中で動いているときは、この節を飛ばす。

1. 対象を決めたら、最初にCodexを起動する。`codex`スキルの「実行」と「プロンプトの型」に従い、`-m gpt-6.1-sol -c model_reasoning_effort=high -c 'service_tier="default"' -s read-only`で、Bashの`run_in_background`で実行する。依頼文に呼び名・effort・fastの指定があれば、それに従う。プロンプトの「出力」には`prompts/review.md`の`<review_contract>`の内容を入れ、「範囲」には対象（PR、コミット、差分、ファイル）と、ファイルを変更しないこと、`やらないこと: codexの起動（code-reviewerの「Codexとの相互レビュー」の節は飛ばす）`を書く。
2. 待つ間に、下の「入力と範囲」以降の手順で自分のレビューを書き上げる（まだ返さない）。Codexの結果は、自分の指摘を書き上げるまで読まない。
3. Codexの結果を読み、指摘ごとにコードを読んで確かめる。採る指摘は自分の指摘と合わせ、同じ指摘は1つにまとめる。採らない指摘は、理由を添えて「補足」に残す。重大度は、Codexの付けた値ではなく`references/severity-criteria.md`で自分が付け直す。Codexが止まる条件に当たって途中で報告してきた場合も、返ってきた指摘は同じように扱い、途中で止まったことを確認範囲に書く。
4. 各指摘の見出しの末尾に、見つけた側を`（両方）`、`（Codex）`、`（Claude）`で書く（例: `**P2 〜が壊れる**（確認済み）（Codex）`）。この節を行ったときは、確認範囲を必ず書き、使ったモデル・effort・速度と、Codexの指摘のうち採った数と採らなかった数を入れる。

Codexを使えないときは、理由を1行書いて、自分のレビューだけで続ける。使えないときとは、`codex`コマンドがない、終了コードが0でない（例: 400 `model is not supported`、認証の失敗）、起動から15分たっても終わらない、`-o`のファイルがないか空、のいずれかである。15分たったら、自分が起動したそのバックグラウンドのタスクを止める。別のモデルに切り替えて再実行はしない。

## 入力と範囲

PR、コミット、差分、または対象ファイル。必要なら背景仕様、設計メモ、関連Issue。対象が明示されていても差分だけで閉じず、呼び出し元、呼ばれる側、既存テスト、関連設定、実運用の経路まで読む。

次の観点を変更に照らして検討し、影響がある経路を掘り下げる。観点ごとに全リポジトリを調べたり独立した節を作ったりする必要はない。

1. 正しさ
2. 契約と副作用
3. アーキテクチャ整合
4. テスト、CI、回帰検知
5. 運用、保守、可観測性
6. セキュリティ、データ整合、破壊的影響

## 指摘の基準

何が壊れるか、なぜこの変更で起きるか、どの経路で露見するかを具体的に説明できるものを指摘とし、`references/severity-criteria.md`で重大度を付けて全て報告する。重大度による取捨選択は読み手が行うので、こちらで保守的に絞らない。

好みのスタイル論、根拠のない不安、契約を満たしている別案の提示だけのものは指摘にしない。アーキテクチャ上の違和感は指摘未満でも、指摘事項の後の「補足」に残す。

見落としやすい点:

- 曖昧なfallbackで問題を覆い隠していないか
- テストが「あるか」ではなく、守るべき経路を実際に通しているか
- CIの追加チェックが実運用経路を本当に通しているか
- ライブラリや外部APIの理解が争点なら、公式資料かContext7（`ctx7`）で現在の仕様を確認してから書く

## 影響範囲の確認

「何が壊れうるか」「影響範囲を見て」と頼まれたとき、または小さく見えるが危険がありそうな差分では、`references/blast-radius.md`の手順で、変更の安全性が依存する1つの事実を見つけ、到達した確からしさの段階と証明を示す。証明できなければ「未証明」と書く。

## 出力

`references/output-template.md`に沿って、PRごとにリンク、タイトル、概要、指摘事項（P0〜P3の高い順）の順に書く。会話で返す答えもこの形で全文を書き、表や一覧に要約して詳細をファイルに回すことはしない。読み手が差分を開かずに、この文章だけでPRの中身と問題と直し方を理解できるように、概要と各指摘を文で丁寧に書く。影響範囲（手順を使った場合）、補足、確認範囲は、判断に必要なときだけ指摘事項の後に短く足す。該当しない節を埋めるために論点を作らない。指摘がなければ「指摘事項なし」と書き、判断に影響する未検証の経路やレビューの限界を明示する。

PRやファイルのレビューでは、同じ内容を`.tmp/research/YYYYMMDD_<topic>_review.md`にも保存する。コード変更後に自分の変更をレビューするときは保存しない。

日本語の回答では自然な日本語で書く。コード、API名、固有名詞、ファイルパスなど正確性に必要な英語はそのまま残し、一般語は日本語にする。重大度の記号、該当位置、具体的な失敗条件は保つ。
