# 影響範囲の確認

変更が差分の外で何を壊しうるかを、出荷前に調べる。「これで何が壊れうるか」「影響範囲を見て」と頼まれたとき、または小さく見えるが信用しきれない差分をレビューするときに使う。

呼び出し元の一覧を作ることは目的ではない。それは検索ですぐ出る。目的は、検索では見えない壊れ方を見つけることである。

## 自分の説明を信じない

もっともらしい影響範囲の説明は、正しくても間違っていても同じくらい説得力がある。だから説明だけを返さない。変更全体の安全性が依存している1つか2つの事実を見つけ、コードを動かして証明する。

### 確からしさの段階

安全性が依存する事実ごとに、手間をかけずに行ける段階まで進め、どこで止まったかを書く。

1. 言っただけ。それだけでは価値がない。
2. 該当する行を示した。実在する`file:line`、またはライブラリ自体のソース。
3. 悪いケースが起こりえないことを示した。失敗の経路を1段ずつたどり、そこに届かないことを示した。
4. 動かした。本物のコードを呼び、間違っていれば大きく失敗するスクリプトかテストを実行した。
5. 動いているアプリで再現した。

段階4は、たいてい、アプリと同じライブラリをimportし、気になっている関数そのものを呼ぶ小さなスクリプト1つで足りる。

## 手順

1. **変更を読む。** 差分、追加・変更・削除されたシンボル、変更後に振る舞いが変わる点。差分に書かれていない部分も含める。PRとコミットの経緯は`gh pr view`と`git log`で読む。経緯が論点になるなら`why`を使う。
2. **安全の根拠になる1つの事実を見つける。** 危なく見える変更の多くは、1つの事実のおかげで安全である。例:「この呼び出しは、すでに無効になったキャッシュの項目を消すだけで、他に何もしない」。その事実が成り立てば、危ないケースの大半が一度に片づく。時間はここにかけ、「もしかしたら」の長い一覧には使わない。
3. **検索が届かない所を見る。** 呼んでいるライブラリのソースを読み、固定されている版とローカルのパッチを確かめる。処理がいつ走るかを考える（マイクロタスク、アンマウントや終了処理、フレームワークごとの違い）。シンボル検索では見えないものをたどる。APIが返すJSON、DBの列、通信の形式、同じバイト列を読む別言語のコード、フィーチャーフラグ、3段先の下流のコード。
4. **リスクごとに正直に評価する。** 起きる見込みと、起きたときの損失を現実的に見積もる。確認できたリスクを残し、確かめて問題なかったものは別に挙げる。実在する`file:line`を示す。検索で何も出なかったことも答えである。呼び出し元やAPIを作り出さない。
5. **その1つの事実を証明する。** 本物のコードを動かす使い捨てのスクリプトか、既存のテストを実行し、何が起きたかを貼る。新しいテストをリポジトリに足すかどうかは、このスキルでは決めない。CLAUDE.mdのテストの規則に従う。
6. **大きい、または広い変更**で、ユーザーがサブエージェントの利用を明示している場合は、同じ問いを複数のサブエージェントに独立に調べさせ、結果を突き合わせる。

## 証明の置き場所

- 証明用のスクリプトは、リポジトリにファイルを残さない。標準入力から渡して実行する（`python3 - <<'EOF'`、`bun -e`、`node -e`など）か、scratchpadに置く。
- `reviewer`サブエージェントとして動いているときはファイルを作れないので、標準入力から実行できる範囲で証明し、それができなければ到達した段階で止めて「未証明」と書く。

## 返すもの

レビュー結果の「影響範囲」の節として、次を書く。

- **変更の中身**: 何が変わったか。分かりにくい部分も含めて。
- **安全の根拠**: その事実、到達した段階、証明。証明できなければ「未証明」と書く。
- **リスク**: 壊れ方、`file:line`、見込みと損失、確かめ方。重要なものには証明を貼る。
- **問題なしと確認したもの**: 確かめた内容と、問題ない理由。
- **マージ前に**: 実際のバグを捕まえる最も安い再現手順か、実行すべき既存のテスト。書いたスクリプトを含める。新しいテストの追加は修正案にしない。

公開される場所（PR、Issue、外部のチャット）に書く前に、私的な情報（社内の事情、個人情報、非公開のURL）を取り除く。
