# レビュールーブリック

## 正しさ

- 条件分岐の抜け、空入力、null、未初期化、境界条件の見落としがないか
- 失敗時、キャンセル時、タイムアウト時、部分成功時の挙動が定義されているか
- 並行実行、再試行、順序逆転、二重実行で壊れないか
- 変更前の契約に依存する既存コードが破綻しないか

## 契約と副作用

- 関数、モジュール、APIの入力/出力契約を暗黙に変えていないか
- 例外、エラー値、ログ、戻り値の意味がずれていないか
- 純粋であるべき層に副作用が漏れていないか
- fallbackで仕様の曖昧さを隠していないか

## テスト、CI、回帰検知

- 変更箇所そのものではなく、実運用経路が検証されているか
- 単体テストだけで満足せず、統合経路やファイル出力経路も守れているか
- CIの新規チェックが、実際に壊れうる経路を通しているか
- 将来のリファクタで簡単に抜け落ちるガードになっていないか

## アーキテクチャ整合

- レイヤ境界と依存方向を破っていないか
- 一時対処のロジックがコア契約として定着していないか
- 責務が別層ににじんでいないか
- 今回の変更が既存のデータフロー、ライフサイクル、所有権の考え方と矛盾しないか

## 運用、保守、可観測性

- 障害時に原因を追えるログ、メトリクス、状態が残るか
- 実害が出てもCIや監視で検知しづらい穴がないか
- 将来の変更で壊れやすい密結合を増やしていないか
- 修正者が意図を読み違えやすい複雑さを持ち込んでいないか

## セキュリティ、データ整合

- 権限境界、信頼境界、危険な入力経路を壊していないか
- データ破損、消失、重複、整合性崩壊の可能性がないか
- 秘密情報や破壊的操作が不用意に露出していないか

## findingの書き方

各findingでは最低限、以下を説明する。

1. 何が壊れるか
2. なぜこの変更で壊れるのか
3. 影響範囲はどこか
4. どの方向の修正でリスクを下げられるか
