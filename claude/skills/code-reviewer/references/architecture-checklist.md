# アーキテクチャ整合チェック

## 境界

- この変更はどのレイヤに属するか
- そのレイヤに置くべきでない責務が入っていないか
- ドメイン、アプリケーション、I/O、UI、インフラの境界をまたいでいないか

## 契約

- 契約定義と副作用実装が分離されているか
- エラー処理、ライフサイクル、所有権の責任者が明確か
- 暗黙の共有状態に依存していないか

## 依存方向

- 下位層が上位層の詳細を知っていないか
- 一時対処として逆方向依存や密結合を増やしていないか

## 実運用経路

- 本番で使う経路とテスト経路が乖離していないか
- CIが守る経路とユーザーが通る経路がずれていないか

## 将来変更コスト

- 次の変更者が`finalize()`や後処理のような重要手順を落としやすくないか
- 成功条件が複数箇所に分散していないか
- 不変条件がコード上に表現されているか

## 観点メモ

findingに満たなくても、以下は指摘事項の後の「補足」へ残す。

- 設計原則との軽いズレ
- 将来の変更で事故になりそうな密結合
- ルール化するとよいパターン
