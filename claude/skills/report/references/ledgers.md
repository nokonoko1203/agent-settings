# 台帳と原稿の形式

すべてUTF-8のTOMLとする。Python 3.11以上の`tomllib`で読む。業務ルートに4台帳を置く。パスはルートからの相対パスとし、ルート外やシンボリックリンクによる逸脱は認めない。検査は通信しない。URLの生存確認だけは`coverage --check-urls`を明示した場合に行う。

## 要求台帳 requirements.toml

```toml
approved_by = "確認者"
approved_at = "2026-11-03"

[[requirement]]
id = "R1"
source = "仕様書 p.1 第1項"
text = "予約方式を比較する"
kind = "提案"
chapter = "01"
depends_on = []
expect = [{ kinds = ["提案"], min = 1 }]

[[requirement.item]]
id = "R1-a"
text = "受付方式と課題"
expect = [{ kinds = ["提案"], min = 1 }, { kinds = ["解釈", "事実"], min = 1 }]
```

`expect`は条件の配列。条件間はAND、`kinds`内はOR。同じ主張IDは何度本文に出ても1件と数える。要求の`expect`はその細部項目全体に適用する。細部項目の`expect`は親からの暗黙継承をせず、明記する。

`kind`は実施・整理・提案・評価。`chapter`は`chapters/`内のファイル名の接頭辞（例`01`）。細部項目を満たす主張は指定した章の本文に必要である。`depends_on`は先行する要求ID。依存する要求がある場合、提案の前提をたどると、その要求の細部項目に結び付いた実証結果に到達しなければならない。

仕様書だけでなく、提案時の約束と打合せの指示も出典を明記して分解する。候補を本人に示し、承認後に`approved_by`と日付`approved_at`を記入する。承認が空なら検査は「細部項目が未承認」の1行で終了コード1。承認後の増減・期待条件の緩和は、本人の再承認が必要である。

## 出典台帳 sources.toml

```toml
[[source]]
id = "S1"
title = "架空の予約運用要領"
publisher = "架空のはるなぎ市"
version = "第1版"
published = "2026-10-01"
retrieved = "2026-11-03"
url = "https://harunagi.example/guide"
sha256 = "原文ファイルのSHA-256を64桁で記入"
reliability = "一次"
path = "sources/guide.txt"
```

`reliability`は一次・二次・報道。`published`と`retrieved`はISO日付。版のない資料は「版表示なし」と明記する。URL・題名・発行者・版を空にしない。同じURLの更新に備え、保存した原文のバイト列のSHA-256を照合する。PDFでは`path`をPDFにし、同じ名前の`.txt`も隣に置く。ハッシュはPDFのものとし、引用照合はテキストで行う。PDFからの抽出の正しさ、引用ページの対応は人が原文で確認する。

## 主張台帳 claims.toml

```toml
[[claim]]
id = "C1-001"
req = ["R1-a"]
kind = "事実"
text = "受付は窓口方式である。"
status = "裏取り済み"
premises = []
alternatives = []
subject = "現行の受付方式"
[[claim.evidence]]
source = "S1"
page = "1"
quote = "受付は窓口方式である。"
```

`req`は細部項目IDの配列。主張IDは`C`で始め、英数字・ハイフン等で区別する。`text`は本文に置く短い主張である。`status`は未確認・裏取り済み・反証あり・人の判断待ち。coverageでは裏取り済みだけが合格となる。「支持しない」という裏取り結果は反証ありとして残す。

全主張で`premises`・`alternatives`・`evidence`を明記する。不要なものは空配列とする。

| kind | 必須の根拠 |
|---|---|
| 事実 | `evidence`に`source`・`page`・`quote`。引用は原文テキストに実在すること |
| 実証結果 | `evidence`に`path`・`value`。成果物のテキストに値が実在すること |
| 解釈 | `premises`に主張ID。すべての枝が事実か実証結果に到達すること |
| 提案 | `premises`と`alternatives`（比較した案の説明の配列） |

実証結果の例：`evidence = [{ path = "artifacts/trial.txt", value = "待ち時間=12分" }]`。表やログの該当ラベルを含めた値にし、偶然の数値一致を避ける。引用照合はUnicodeの互換正規化と空白・改行の除去をして行う。原文にない省略や言い換えは許さない。事実・実証結果の数値は引用か値に必要である。意味の支持、単位や条件の正しさは裏取りで確認し、文字列検査の合格だけで裏取り済みにしない。

`subject`は一貫性を確認する同一の対象と条件のキー。使わない場合も`subject = ""`と書く。例：`予約受付の推奨方式`。同じ対象・条件を章間で繰り返す推奨は、台帳の`text`を同じ文で記録する。機械は同一キーの数値と推奨文を比較する。それ以外の文の不一致はPENDINGにし、条件と言い回しを人が確認する。条件や時点が違う記述は別のキーにする。推論の判定へ無関係な主張を前提として追加して、このPENDINGを解消しない。

## 用語台帳 glossary.toml

```toml
[[term]]
correct = "予約システム"
wrong = ["予約システムー"]
```

`wrong`は部分一致で落とす綴りの配列。引用で正当な表記まで落とす語は登録しない。空の一覧は`term = []`と書く。

## 本文 chapters/*.md

章の順序はファイル名順。検査可能な単位を物理行で分け、その行の末尾に対応する主張IDを置く。複数の主張を1行に置く場合は、文もIDも台帳の順に並べる。空白・改行以外の言い換えは、まず台帳を更新し、その後本文へ反映する。主張の文は1行内に置き、行折り返しはエディターの表示で行う。

```markdown
# 受付方式

受付は窓口方式である。[C1-001]
```

見出し、空行、1行のHTMLコメントは本文照合の対象外。箇条書きの先頭記号は取り除いて照合する。表やコード、画像の説明も自由記述の抜け道にせず、主張として登録する。図表のキャプションは行頭`図1:`・`表1:`（全角コロンも可）。キャプション全体を主張として登録する。本文側の`図1`等の参照にも主張IDが必要である。番号の重複・欠番・参照先なし・未参照のキャプションを落とす。図と表はそれぞれ1から連番にする。

## 推論判定と人の承認 reviews/

`logic --judge CMD --judge CMD`は、結論1つと直接の前提の`id`・`kind`・`text`だけをJSONで標準入力へ渡す。シェルは使わずコマンドを引数分割して起動する。実行場所は業務ルート。パイプやリダイレクトが必要ならラッパーを用意する。

```json
{"conclusion":{"id":"C1-002","kind":"解釈","text":"受付経路は限られる。"},"premises":[{"id":"C1-001","kind":"事実","text":"受付は窓口方式である。"}]}
```

出力は`{"verdict":"成立","reason":"理由"}`だけを標準出力へ出す。verdictは成立・飛躍あり・矛盾。判定の失敗・不正JSON・120秒のタイムアウトは検査不能（2）。標準エラーや入力全文はエラー報告へ転載しない。

両方が飛躍あり、または一方でも矛盾ならFAIL。判定が割れた場合と1判定だけの飛躍ありはPENDING。指定なしもPENDING。全判定が成立ならPASS。通常のPENDINGは0、`--strict`では1になる。構造・一貫性のFAILは人の推論承認では免除しない。

結論・前提の文、種類、IDを安定順でJSON化したSHA-256を論証ハッシュにする。`reviews/logic.json`に入力・各判定・判定コマンドの指紋を残す。同じハッシュかつ同じ判定コマンドなら再利用する。実行ファイルと、その直後に指定したスクリプトの内容も指紋に含める。後続の引数のファイルは出力先の可能性があるため読まない。モデルや指示文を切り替えたらコマンド引数にも反映する。人の許容は別ファイルに記録する。

```toml
# reviews/logic-accepted.toml
[[accepted]]
id = "C1-002"
hash = "logicの出力に表示された64桁の論証ハッシュ"
reason = "不足する条件を協議事項として明記するため許容する"
approved_by = "確認者"
```

前提か結論が変わると承認は失効する。承認者や理由をAIが代筆して承認済みにしない。

## 出力・納品

項目・主張・原稿の行ごとにPASS/FAIL/PENDINGと理由を出し、最後に件数を示す。0はFAILなし、1はFAILまたは未承認、2は台帳・判定コマンド等の検査不能。strict時はPENDINGも1。buildはcoverageを再実行し、根拠を前提の先までたどって脚注を生成する。既存ディレクトリか拡張子なしの出力先には`report.md`を作る。

build単体は推論・人の承認を証明しない。納品前の検証はMakefileの`build`（coverageとstrict logicを先に実行）で行い、骨子と提案の本人確認を証拠に残す。

mutateは合格した題材の一時コピーだけに7種類の誤りを各1件仕込む。構造の3種類はlogic、本文・引用の4種類はcoverageが落とすことを確認する。推論は成立を返すスタブを使うため、構造エラーをAIの判定で偶然拾った結果にはならない。題材には、数値、引用、前提、別章にある同じsubjectの提案が必要。題材不足は2、検出漏れは1。
