# 機能の追加・変更

1. `how`で、影響するサブシステムの仕組みを読む。プロジェクトに`verify-<app>`スキルの機能一覧やe2eがあれば、変更する機能のファイルと、それを確かめているe2eも読む。
2. ロジックを書く前に、データの形を決める。散らばったフラグより状態の遷移、分岐の連続より対応表、同じ形の仮定の繰り返しより型を選ぶ。既存の形で足りるなら、新しい構造は足さない。既存のif/elseに分岐をもう1つ足す、別のフラグと同期させる必要があるフラグを足す、という形になったら、構造が足りていない。
3. 関数やモジュールの境界をまたぐ変更では、先に呼び出し側の使い方を書き、そこから型とシグネチャの下書きを作る。レベル2では仕様書に入れる。実装中に下書きと合わない箇所が出たら、黙って吸収しない。下書きが間違っていたのか、要件を見落としたのか、実装がやりすぎなのかを判断する。
4. 小さく区切って実装し、区切りごとに`make check`などで確かめてから次に進む。振る舞いを変えたら、機能一覧の説明と、e2eのケースも同じ変更で直す。既存のケースの期待値を変えるのは、仕様の変更に根拠があり、ユーザーが承認したときだけにする。テストを通すために期待値を弱めない。対応表を持つプロジェクトでは、抽出をやり直し（`e2e-inventory-sveltekit.ts write`など）、変更で増えた確認対象をケースか理由付きの例外で受け持たせ、足りないe2eのケースは`write-e2e-case`で書いて対応表に載せる。対応表がなければ、新しいケースは候補を示して人に選んでもらう（`spec`）。
5. ユーザーが使うのと同じ画面や経路で確かめる。プロジェクトに`verify-<app>`スキルがあれば使う。e2eがあれば完了前に動かし、ケースごとの結果（成功・失敗・不安定・スキップ・未実行）を証拠に残す。数分で終わるなら全件動かす。長くかかる場合は、対応表があれば`select`で変更からケースを選び、対応表から引けない変更は利用先を調べてケースを足す（`~/.claude/references/verification-map.md`）。動かしたケースと選んだ理由を書く。スキップや未実行を成功に数えない。e2eが確かめない範囲は実操作で確かめ、確かめられなかった範囲は報告する。結果がはっきりしないものや、別の経路での確認は合格にしない。
6. 設計に争点が残る場合は、`/codex:adversarial-review`などの別の視点のレビューを、報告の中で提案する（実行はユーザーの明示がある場合だけ）。

報告: 作ったもの、選んだ設計とその理由（案を比べた場合は表）、未決定のこと。
