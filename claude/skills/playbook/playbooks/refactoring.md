# リファクタリング

構造を変え、振る舞いは変えない。計画は`spec`の「リファクタリングの場合」と`refactor-plan-template.md`で書き、手順はここに従う。

1. 先に、今の振る舞いを固定する方法を決める。既存のテスト、または新旧の出力を比べる使い捨てのスクリプト（`.tmp/evidence/<task>/`）を使う。型検査とlintは固定にならない。新しいテストで固定するのは、ユーザーが示した場合だけにする。
2. `how`で今の仕組みを読み、足りない構造を言葉にする。形が既に明らかで局所的なら、そのままにする。分岐や不正な状態を減らさず、間接層を増やすだけの形は採らない。
3. 目指す形を書く。今の要件で一から作るなら、モジュールの分け方、型、呼び出しの関係がどうなるか。
4. 足す前に消す。使われていないコード、呼び出し元が1つしかない包み、重複した検証、参照されていないものを先に消し、そのうえで新しい形を作る。目指す形に届く最小の変更だけを入れ、「ついでに整理すると良さそう」な変更は戻す。
5. 小さく動かし、1回ごとに手順1の方法で振る舞いが変わっていないことを確かめる。APIの形を変える場合は、呼び出し元を全部移し、古いAPIを同じ回で消す。互換のための層や、新旧を並べた経路は残さない。名前の変更は、文字列、文書、コメントの中の参照まで、実際のファイルで確かめる。最後に、型検査やビルドが通ることではなく、実際の出力で振る舞いが変わっていないことを確かめる。大きな変更では、新旧の出力の差分、記録した基準の再生、ユーザーが使う画面や経路での実行のいずれかで、同じ結果になることを示す。
6. 読み手の負担が減ったかを確かめる。たどる層の数と、覚えておく必要のある状態の量で見る。どこかで減っていなければ戻す。

途中で不具合や機能の不足が見つかったら、混ぜずに報告し、構造の変更を先に終える。設計の作り直しが必要になったら、featureとして扱う。

報告: 変わった構造、振る舞いを固定した方法、変わっていないことの証拠、戻したもの。
