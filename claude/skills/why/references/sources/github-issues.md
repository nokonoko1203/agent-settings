# Issue・チケット（GitHub Issues）

## 含まれるもの

- 機能や不具合と、その動機を説明するIssue
- 動機の種類を示すラベル（`bug`、`enhancement`、`customer`、`incident`など、リポジトリ固有のもの）
- 範囲の変更、明確化、「なぜやるか」が書かれたコメント
- マイルストーンやGitHub Projectsの項目（期限や取り組み単位と結びつける）
- Issueにリンクされた、またはIssueを閉じたPR

「顧客Xに頼まれたから」「Q3のコンプライアンス対応のため」といった、プロダクトや事業の文脈はここにあることが多い。

## 調べ方

1. **リンクされたIssueから始める。** 起点のコミットやPRがIssue番号（`#1234`、`Fixes #567`）を参照していれば、先に`gh issue view <number> --comments`で全文とコメントを読む。PRの`closingIssuesReferences`も使う。
2. **キーワードで探す。** `gh issue list --search '<語> in:title,body' --state all`、または`gh search issues '<語>' --repo <owner>/<repo>`。機能名、主要なシンボル、業務の用語で、言い方を変えて複数回検索する。
3. **親子や関連をたどる。** サブIssueやタスクリストに入っていれば親を読む。親の方に「なぜ」が書かれていることが多い。重複として閉じられたIssueは、元のIssueまでたどる。
4. **ラベルとマイルストーンを見る。** 動機の種類と期限が分かる。
5. **別のトラッカーがある場合。** Linear、Jira、Backlogなどが接続されていれば、同じ手順をそのMCPで行う。

## よい証拠の例

- 事業上の問題を書いたIssue本文:「顧客AcmeはSOC2監査のためにXが必要」
- 判断を記録したコメント:「案Aは課金サービスに触る必要があるので案Bにする」
- 取り組み単位の親Issueやマイルストーン:「エンタープライズ対応」「決済失敗の削減」

## よくある落とし穴

- **範囲のずれ。** PRが参照するIssueが、いったん閉じて別の範囲で再開されていることがある。履歴全体を読む。
- **形だけのテンプレート。** 「なぜ」の欄が決まり文句（「UXの改善」）で埋まっているなら、本当の答えではない可能性が高い。
- **古いIssue。** 計画が変わる前の版を反映していることがある。日付を確かめ、コードが出荷された日と照らし合わせる。
- **見られないIssue。** 権限がなければ、推測せず欠落として記録する。

## 返すもの

関係するIssueごとに、番号とタイトル、本文やコメントからの動機の引用（言い換えない）、ラベル、親Issue、マイルストーン、作者、作成日、クローズ日、URL。
