# 動いた証拠

振る舞いが変わる変更（画面、CLI、APIの出力や副作用）は、実際に動かして確かめ、その証拠を人が短時間で判定できる形で残す。レビューする人と`code-reviewer`は、コードではなくこの証拠で「動いたか」を判定する。

## 置き場所

- 対象リポジトリの`.tmp/evidence/<task>/`。`<task>`はCLAUDE.mdの「作業の重さ」で決めたタスクID（`<YYYYMMDD-HHMM>-<短い英字の名前>`）。
- 中身は`evidence.md`と、スクリーンショット、ログ、出力などのファイル。
- `.tmp/`がgitの無視対象でなければ（`git check-ignore -q .tmp/x`が失敗すれば）、`.git/info/exclude`に`.tmp/`を1行足す。リポジトリの`.gitignore`は変えない。
- `evidence.md`は、最後のコード変更より後に書く。証拠を書いたあとでコードを直したら、確かめ直して書き直す。終了時のhook（`evidence-check.sh`）は、振る舞いに関わるファイルより古い`evidence.md`を証拠と認めない。

## 形式

```markdown
# <作業の題名>

- タスク: <task>
- 対象: <ブランチ、base..head、または作業ツリー>
- 確かめた日時: <UTC>

## 受け入れ条件と証拠

| 条件 | 確かめ方 | 結果 | 証拠 |
|---|---|---|---|
| <受け入れ条件> | <操作やコマンド> | 合格 / 不合格 / 未確認 | <ファイル名、または下の節> |
| 異常系: <受け入れ条件> | <操作やコマンド> | 合格 / 不合格 / 未確認 | <ファイル名、または下の節> |

## 仮説

| 仮説 | 根拠 | 確かめ方 | 正しければ観測されるもの | 結果 |
|---|---|---|---|---|

## 実行したコマンド

（コマンド、終了コード、出力の抜粋）

## e2eの結果

| ケース | 確かめた範囲 | 結果 | 証拠 |
|---|---|---|---|
| <ケース名またはID> | <例: 件数の表示。線の描画は含まない> | 成功 / 失敗 / 不安定 / スキップ / 未実行 | <結果ファイル、スクリーンショット> |

## 画面

- <操作> → <結果>（スクリーンショットのファイル名、またはARIAスナップショットの抜粋）
- console: エラー0件（あれば一覧）
- network: 失敗したリクエスト0件（あれば一覧）

## 確かめていないこと
```

該当しない節は省く。ただし、レベル1・2の作業では、「受け入れ条件と証拠」の異常系の行（当たる観点がなければ「異常系: 該当なし: <理由>」の行）と、「確かめていないこと」の節（なければ「なし」）を省かない。`spec`の確認範囲表で「確かめない」とした観点は、「確かめていないこと」に写す。「仮説」の節は、不具合の修正と性能の改善で書く（`playbook`）。終了時のhook（`evidence-check.sh`）は、レベル1・2で異常系の行か「確かめていないこと」の節がない`evidence.md`を証拠と認めない。表の「結果」は実際に観測したものだけを書き、観測していなければ「未確認」とする。

e2eの結果は、その回の実行結果のファイルから書く。実行前に前回の結果ファイルを消すか移し、古い結果を読まない。再試行で通ったものは「不安定」、結果にないケースは「未実行」とし、どちらも成功に数えない。e2eが確かめない範囲は、実操作で確かめた結果を「受け入れ条件と証拠」の表に書き、確かめなかったものは理由を「確かめていないこと」に書く。モックを相手に確かめた結果と、実際の認証や外部サービスに接続して確かめた結果は、「確かめ方」の欄に「モック」「実接続」と書いて区別する。

振る舞いが変わらない変更（文書だけ、型だけ、実行時に効かない設定）では、`evidence.md`に`動作確認なし: <理由>`の1行だけを書く。

## 取り方

- プロジェクトに`verify-<app>`スキルがあれば、それに従う。
- なければ、使える手段で取る。
  - **画面**: ブラウザペインで実際に操作する。ARIAスナップショット（`read_page`）、console、networkをテキストで`evidence.md`に書く。ブラウザペインのスクリーンショットはファイルに保存できない。PR本文に載せる画像は、そのリポジトリにあるPlaywrightなどで撮り、`.tmp/evidence/<task>/`に保存する。撮る手段がなければ、ブラウザペインの画像を会話に表示し、`evidence.md`には何を表示したかを書く。
  - **CLI**: コマンド、終了コード、標準出力と標準エラーの抜粋。ファイルを書く処理なら、書かれた中身も確かめる。
  - **API**: リクエスト、ステータス、レスポンス本文の抜粋。DBなどの副作用も確かめる。
- 内部のsetterやテスト専用のエンドポイントではなく、利用者と同じ経路を通す。最後の画面だけでなく、操作とその結果の状態を残す。

## PR本文への載せ方

PR本文の「確認」の節で、レビューする人が動いた様子をPR上で見られるようにする。

### 画面

- 受け入れ条件を確かめた画面の画像を載せる。前後の比較は、判断に要るときだけ並べる。
- 本文は`.tmp/evidence/<task>/pr-body.md`に書き、画像は同じディレクトリに置く。「画面」の小節に表を置き、見出しかセルに「操作 → 結果」を書き、セルに`![<操作 → 結果>](./<ファイル名>)`を書く。
- `gh pr create --body-file .tmp/evidence/<task>/pr-body.md --attach .tmp/evidence/<task>/<ファイル名>`のように、本文で参照した画像をすべて`--attach`で渡す。ghが本文の参照をアップロード後のURLに書き換える。本文のパスは`pr-body.md`のあるディレクトリからの相対で書く。PRを作ったあとは`gh pr edit`か`gh pr comment`で同じように渡す。
- `--attach`はgh 2.99.0以上で使える。`gh --version`が古いか、`--attach`が失敗したら、画像を載せずに理由を1行書き、ユーザーに伝える。添付の一部が失敗してもPRは作られるので、終了コードが0でなければPRの本文を開いて確かめる。
- 小節の冒頭に「モック」か「実接続」かを1行書く。
- 撮る手段がない場合は、画像を載せない理由を1行書く。

### API

- 受け入れ条件ごとに、コードブロックで次を貼る。
  - リクエスト: `curl`で再現できる形（メソッド、URLのパス、判断に要るヘッダ、本文）
  - ステータス
  - レスポンス本文の抜粋。判断に要る部分だけを残し、長い配列は先頭の数件と件数にする
- 「モック」か「実接続」かを書く。DBなどの副作用を確かめたなら、その結果も添える。

### 載せないもの

- `Authorization`、Cookie、APIキー、トークン、署名付きURLの値は`***`に置き換える。
- 個人情報や顧客のデータが写る画面・本文は載せない。テスト用のデータで撮り直すか、載せない理由を書く。
- 公開リポジトリのPRに、非公開のリポジトリや案件の画面・データを載せない。載せる前に画像を開いて、写っているものを確かめる。

## `[human]`の条件

`[human]`を付けた条件は、人が見て判定する。人がすぐ判定できるように、見るための材料（スクリーンショット、見る手順、URL、起動コマンド）を`evidence.md`に用意する。結果の欄は「ユーザーの確認待ち」とする。
