# 不具合の修正

すべての変更は、実行して得た証拠に結び付ける。「念のため」の変更は仮説であり、入れない。

1. 自分で先に再現する。ユーザーが不具合を見た画面や経路で再現する。プロジェクトに`verify-<app>`スキルがあれば使う。ユーザーに再現を頼むのは、自分の手段では届かない理由を具体的に示せて、届くところまで試した後だけにする。そのまま再現しなければ、条件を絞る、ログを足す、きっかけを人工的に作る。
2. 原因を二分探索で絞る。候補になる仮説を並べ、残りの範囲を一番大きく減らせるものから確かめて消していく。仮説の材料は、`how`（関係する仕組み）と`why`（最近の変更と退行の経緯。`git log`、`git bisect`）。状態が分からなければ、推測せずにログや計測を足して実際の値を読む。契約の前に足したログや計測、`git bisect`の扱いは、`SKILL.md`の「作業の重さとの関係」に従う。
3. 根本原因まで「なぜ」をたどる。nilチェックや例外の握りつぶしで症状だけを消さない。同じ書き方の箇所を`rg`で探し、同じ原因のものを全部挙げる（直すかどうかは範囲の判断）。再起動後に起きる不具合は、コードより先に、残った状態（設定ファイル、キャッシュ、ロックファイル、保存された状態）を疑う。
4. 根拠のある最小の変更だけを入れる。否定された仮説のために入れた変更は戻す。
5. 手順1と同じ画面や経路で確かめる。修正前に失敗し、修正後に通る出力を、そのまま`evidence.md`に貼る。別の経路で通っただけや、結果がはっきりしないものは合格にしない。単体テストが通っても、不具合がなくなった証拠にはならない。
6. 原因を見つけるのに深く掘る必要があった場合は、次に最初の段階で気づけるログや表示を、報告の中で提案する（実装はしない）。

原因の診断だけを頼まれた場合（メモリリーク、CPUの空回り、表示の乱れなど）は、手順3で止める。プロファイルなどの記録を取り、仕組みを確かめ、原因のファイルと行を報告する。

報告: 何が壊れていたか、根本原因、修正、確かめ方、修正前と修正後の出力。
