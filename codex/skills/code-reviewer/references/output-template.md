# レビュー結果

会話で返す答えと、`.tmp/research/`に保存するファイルの両方を、この形で書く。会話で表や一覧に要約し、詳細をファイルに回すことはしない。読み手は差分もPR本文も開かず、この文章だけで、PRが何をするものか、何が問題で、どう直せばよいかを理解できなければならない。

## 形

PRごとに次の4項目を、この順で書く。複数のPRを扱うときは、PRの数だけ繰り返し、PRの間を区切り線（`---`）で分ける。表にはしない。PR以外（コミット、差分、ファイル）のレビューでは、リンクとタイトルの代わりに対象（コミットハッシュ、ファイルパスなど）を書く。

```markdown
### #123

- **リンク**：[owner/repo#123](https://github.com/owner/repo/pull/123)
- **タイトル**：feat(web): 〜する
- **概要**：
  - これまでどうなっていて、何が困っていたか
  - このPRが何を変えるか（主な変更を、利用者や開発者から見た振る舞いで）
  - 実際に動かして確かめた結果（確かめた場合）
- **指摘事項**：
  - **P2 <何が問題かを一文で>**（確認済み）
    - 何が起きるか。どの条件で、どこで、どう壊れるか
    - なぜこの変更で起きるか
    - 影響
    - どう直すとよいか
```

## 概要

PR本文の言い換えではなく、自分の言葉で書く。背景（これまでどうだったか）、変更（何が変わるか）、確かめた結果を、それぞれ1〜3文で書く。差分を見ていない人が読んでも、変更の目的と中身が分かるようにする。PR本文と実際の差分が違うところは、概要ではなく指摘事項に書く。

## 指摘事項

- 重大度（`references/severity-criteria.md`のP0〜P3）の高い順に並べる。
- 各指摘は、太字の一文の見出しと、その下の短い文の箇条書きで書く。「発生条件:」「影響:」のようなラベルを並べた穴埋めにせず、文として読めるように書く。
- 何が起きるか、なぜこの変更で起きるか、影響、直し方を必ず含める。専門用語や関数名を出すときは、それが何をするものかを一言添える。
- 実際に動かして確かめたものは「確認済み」、コードから推定したものは「推定」と見出しに付ける。
- 複数のPRの組み合わせで起きる問題は、関係する各PRの指摘事項にそれぞれ書き、相手のPRへのリンクを付ける。
- 指摘がなければ「指摘事項なし」と書き、何を確かめて問題が無かったかを一文添える。

## ファイルの書き方

- 手元のブランチにあるファイルは、リポジトリのルートからの相対パスのMarkdownリンクにする。
- PRのブランチにだけあるファイル（手元のmainに無いもの）は、`https://github.com/<owner>/<repo>/blob/<コミット>/<パス>`のリンクにする。ファイル名だけを`インラインコード`で書かない。
- URLの一部やファイル名の例のように、ファイルを指さない文字列は、ファイルを指していないと分かる書き方にする（例: 「URLの`/error/index.html`」）。

## 指摘事項の後に置けるもの

判断に必要なときだけ、指摘事項の後に次を短く足す。該当しなければ書かない。同じ問題を複数の節へ重ねない。指摘がないことを埋め合わせるための懸念は加えない。

- 影響範囲: `references/blast-radius.md`の手順を使った場合だけ。安全の根拠になる事実、到達した確からしさの段階と証明（または「未証明」）、マージ前に実行する最も安い確認。
- 補足: 指摘未満の設計上の注意、未確定の仕様、残るリスク。
- 確認範囲: 確認した経路と証拠、判断に影響する未実施の確認。
